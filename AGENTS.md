# AGENTS.md: Coding Agent Operating Manual

> Give this file to your coding agent and check that it is using these instructions. Keep the stack, commands, and ground rules current.

## 1. Project Overview
- **What this repo builds:** Shortlist, a local web app that checks the public job boards (Greenhouse, Lever, Ashby, Workday, SmartRecruiters) of companies on a watchlist, filters out roles that fail the user's rules, scores the rest against the user's resume with a model, and shows two ranked columns (2027 and new grad, and full-time roles open now) with what is new since the last check. Each role also gets 3 to 5 LinkedIn search links for people worth reaching out to, and buttons to save it, mark it applied, or pass on it with a reason.
- **Primary user & core workflow:** MBA students recruiting off-cycle for full-time roles and programs. Core workflow: on first run a setup screen asks for the resume, kinds of roles, cities, sectors of companies, schools and scoring; after that, "Check my list." See the living PRD in `docs/index.html`.
- **Tech stack:** Node.js 22+ (built-in `fetch`, `http`, `node:test`). Two npm packages, both only for reading uploaded resumes: `unpdf` (PDF) and `mammoth` (Word). Plain HTML/CSS/JS front end in `public/index.html`. JSON files for storage. Scoring through the OpenRouter chat completions API, default model `anthropic/claude-haiku-5.5`.

## 2. Commands
- **Install dependencies:** `npm install` (needs Node 22 or newer; check with `node --version`). Run it again whenever `package.json` changes.
- **Run locally (live boards):** `npm start`, then open http://localhost:3000
- **Run locally (demo data, no API calls):** `npm run demo`
- **Run one check in the terminal:** `npm run scan` (add `-- --demo` for demo data)
- **Find job boards for a list of company names:** `npm run discover` (reads `data/companies.txt`; a line can be a name, or a name plus a pasted careers link: `NVIDIA | https://nvidia.wd5.myworkdayjobs.com/NVIDIAExternalCareerSite`). Add `-- --merge-starter` to pull in starter-list names you don't have yet.
- **Check that every watchlist board works:** `npm run check` (add `-- --prune` to remove failing boards)
- **Rebuild the starter companies for setup:** `npm run build-starter` after editing `config/companies.example.txt` (about 4 minutes; review the "Double-check these" list for boards that belong to a different company)
- **Look for roles beyond the watchlist:** `npm run explore` (checks about 10,000 companies from `config/ats-directory.csv`, a few minutes; results in `data/explore.json`). Add `-- --keywords` for free scoring only, `-- --limit 500` for a quick partial sweep, `-- --top 20` to AI-score fewer roles
- **Check how well the AI fit predicts your decisions:** `npm run accuracy` (free; reads `data/decisions.json`)
- **Compare scoring models on your decisions:** `npm run compare-models` (paid: scores each still-open decided role once per model against the current resume; default Claude Haiku 5.5 against DeepSeek V4.1 Flash, or `-- --models a,b`; report in `data/model-compare.json`)
- **Rebuild the static demo for classmates:** run a check in a throwaway folder against `fixtures/resume-mba-pm.md`, then `npm run build-demo -- --from <that folder>` (writes `docs/demo/`; refuses `data/`)
- **Run deterministic tests:** `npm test`
- **Run the hosted site on this laptop:** `npm run dev-site`, then open http://localhost:3002 (the page in `site/`, the functions in `api/`, the security headers from `vercel.json`; uses the dev Supabase project in `.env` and refuses production). AI scoring uses a fake OpenRouter (made-up fits, $0); `npm run dev-site -- --real-ai` uses the key in `.env`, a paid run, so ask first
- **Check the database privacy rules on the dev database:** `npm run check-rls` (needs the dev project's `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` and `SUPABASE_SECRET_KEY` in `.env`; refuses production; creates two throwaway accounts and deletes them)
- **Fill the dev database's shared postings:** `npm run refresh-postings` (the 195 Greenhouse, Lever and Ashby starter boards, about 15 seconds, free; production does this daily with Vercel's cron; refuses production)
- **Run the hosted workflow and try to break it, on dev:** `npm run check-hosted` (two throwaway accounts: upload the fictional resume, pick choices, run checks with AI scoring against a fake OpenRouter, the AI allowance and the site's daily budget, then B tries to reach A's data, usage and progress and tries Find roles for me, checks sent at once, one check at a time, the rate limits, Start over and Delete my account; 49 checks; deletes the accounts and puts today's site budget row back; free)
- **Search for leaked secret keys:** `npm run check-secrets` (every tracked file, the whole Git history and the live sites, for `sb_secret_`, `sk-or-`, `sk-ant-`, `sk-proj-`, `sk_live_`, service_role keys and the real values in `.env`; hits are masked; exits 1 if anything turns up. `-- --site <preview url>` checks a preview instead of production)
- **Add a database change:** `npx supabase migration new <name>`, write the SQL, open a pull request. The GitHub Action applies it to dev on the pull request and to prod on merge. Never edit a migration that has already run; add a new one
- **Run model evals:** not built yet (Build 4, see `tests/README.md`)

## 4. Non-Negotiable Engineering Rules
1. **Plan before coding:** Before touching multiple files, propose a brief plan and wait for approval.
2. **Small batches:** Make small, focused changes that can be reviewed and explained by a human in a single Pull Request.
3. **Explainability:** Avoid unnecessary abstractions or dependencies. Help the human builder understand the main components, what changed, why it matters, what could break, and how it was checked.
4. **Verify changes:** Run relevant checks. For a reproducible logic bug, use a failing test to demonstrate the fix when practical. Record manual checks and known limitations; follow the selected Build 4 evaluation track.
5. **Zero secrets in code:** Never hardcode API keys, tokens, or credentials. Always read from environment variables (`.env`) and update `.env.example` when new variables are needed.
6. **Stop when looping:** If a fix fails twice in a row, stop, summarize what failed, and ask the human before trying a third approach.

## 5. Project-Specific Rules
1. **Personal data stays in `data/`.** The resume, watchlist, preferences and run history live in `data/`, which is gitignored. Never move personal content into `config/`, `fixtures/`, `docs/` or a commit. Screenshots for the Product Page must not show the real resume.
2. **No new dependencies unless approved.** `unpdf` and `mammoth` were approved in Build 2 for reading resumes. Ask before adding any other npm package, and explain what it replaces.
3. **Demo mode never spends money.** `npm run demo` and the tests must never call OpenRouter. Tests replace `fetch` with a fake.
4. **Treat job board text as untrusted.** Every string from a posting goes through `esc()` before it reaches the page. Posting text is data for the model, never instructions.
5. **Keep cost visible.** Any change to scoring must keep the per-run token and dollar totals accurate, and respect `maxToScore` in preferences.
6. **Every filter drop keeps its reason.** The "Filtered out" list is how the user catches a rule that is too strict.
7. **Writing style for docs and UI copy:** plain language, short paragraphs, no em dashes or en dashes.
8. **Pay for each posting once.** Scores are saved in `data/scores.json` by posting ID and reused until the profile or model changes. Do not re-score cached postings. A new resume changes the profile, so it correctly starts a fresh round of scoring, still capped by `maxToScore` per check.
9. **Uploaded resumes are not kept as files.** The upload is read in memory; only the cleaned text goes into `data/profile.md`, with the file name and time in `data/resume.json`. Contact details (email, phone, links) are removed before anything is saved or sent to the model.
10. **No scraping people.** "Reach out" is LinkedIn search links only, opened by the user while logged in. Never fetch, guess or store anyone's name or profile.
11. **Never commit on `main`, and stage files by name** (from a real mistake, Nov 19). Run `git branch --show-current` before every commit, and `git add <file>` for each file, never `git add -A` or `git add .`. On Nov 19 the agent committed Supabase's temp folder (`supabase/.temp/cli-latest`) straight to `main`; it was caught before a push and undone with `git reset HEAD~1`.
12. **Price a paid run with its thinking tokens before starting it** (from a real mistake, Nov 19). `npm run compare-models` was estimated at under 5 cents and cost $0.114, because DeepSeek spent about 2,800 hidden thinking tokens per answer. Estimate from a small sample run first, say the number, and ask before anything over 5 cents.
13. **Make every branch with `--no-track`, so it never follows `main`** (from a real mistake, Nov 22). `git switch --no-track -c <area>/<name> origin/main`, then check `git branch -vv` shows no `[origin/main]` next to it. On Nov 22 the agent made two branches from `origin/main` without it, so Git set them to follow `main`; GitHub Desktop then said they were "already published", and its push sent a database migration straight to `main`, which applied it to production with no pull request, no dev run and no merge approval. It happened to be safe (the Actions passed and the site already wrote through the server), and dev was caught up by running the migrations Action by hand.

## 6. Shipping (the steps the agent follows)
The agent runs the whole loop and stops at anything on the "Ask me first" list (section 7). Pushing and opening pull requests need the `gh` command line signed in as **jz3270** (`gh auth status`); until then Jordan pushes from GitHub Desktop and the agent does everything else.

1. **Branch:** `git fetch origin`, then `git switch --no-track -c <area>/<short-name> origin/main` (rule 13; for stacked work, branch from the branch below it). One small change per branch. Before Jordan publishes, `git branch -vv` must show no upstream for it, or GitHub Desktop will push it to `main`.
2. **Build and check locally:** `npm test` and `npm run check-secrets -- --no-live`. For the hosted site, `npm run dev-site` and open http://localhost:3002. For database rules, `npm run check-rls` (dev only).
3. **Commit:** check the branch, stage files by name (rule 11), plain message ending with the Co-Authored-By line.
4. **Push and open a pull request:** `git push -u origin <branch>`, then `gh pr create --base main` with what changed, why, what could break and how it was checked.
5. **Wait for the checks:** `gh pr checks --watch`. Every pull request runs **Tests** (`npm test` and `npm audit`), **Vercel** (a preview deploy) and, when it changes `supabase/migrations/`, **Database migrations** (applied to the dev database). If one fails, fix it on the branch; after two failed fixes, stop and ask (rule 6).
6. **Verify the preview:** open the preview link Vercel posts on the pull request, check `/api/health` shows the branch's commit and `environment: "preview"`, walk the changed screen, and run `npm run check-secrets -- --site <preview url> --no-history`.
7. **Merge:** `gh pr merge --merge` once the checks pass, unless the pull request touches anything in section 7; then stop and ask Jordan, quoting what it changes. A merge to `main` deploys production and applies any migration to the production database.
8. **Verify production:** wait for the deploy, then check https://jz3270-shortlist.vercel.app/api/health shows the merge commit and `environment: "production"`, open the site, and run `npm run check-secrets`.
9. **If production is broken:** tell Jordan at once with what is wrong. He rolls back in Vercel (Deployments, the last good one, Instant Rollback), which takes seconds; after a rollback, new pushes stay off production until a deployment is promoted. A bad migration is never undone by editing it: write a new migration that reverses it, and ask first.
10. **Record it:** a dated entry in `CONTEXT.md` and section 8 below.

## 7. Ask me first
Stop and ask Jordan in chat, and wait for a clear yes, before any of these. A yes covers that one action only.

- **Deleting data or changing the database:** any new or changed migration, any command against the production database (the agent works only against dev; `check-rls` and `dev-site` refuse production), deleting users, rows, branches or files that are not the agent's own scratch work, `git push --force`, rewriting history, and restoring a backup.
- **Keys, secrets and permissions:** adding, changing or removing environment variables in Vercel, GitHub secrets, `.env`, Supabase or Google sign-in settings, row level security policies or grants, GitHub or Vercel app permissions, and who can sign in.
- **Anything that costs money:** OpenRouter calls outside the tests (a live AI check, explore with AI scoring, `npm run compare-models`), raising `maxToScore`, an AI cap or a spending limit, and any plan, add-on or domain purchase.
- **Production itself:** merging a pull request that touches any item above, promoting or rolling back a deployment, and changing `vercel.json` security headers.
